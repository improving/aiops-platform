# The platform issues workload credentials, never its own user tokens

SDKs, CI jobs and model clients cannot use a browser login, and vector databases and inference servers
each carry their own credential mechanism.
Automation calls the API with OAuth2 client credentials issued by Keycloak (one confidential client per system,
scoped to one organization), and each deployed vector database or inference endpoint gets a per-instance
credential (Qdrant API key, Milvus user and password, vLLM or TGI `--api-key`) generated by the control plane,
stored in a Kubernetes Secret next to the release, and shown once to the owner in the UI.
The platform does not mint or sign tokens of its own.

## Considered options

- Platform-issued JWTs or personal access tokens: a second issuer to secure, rotate and revoke; deferred until a CLI exists.
- Reusing one shared key across all instances of a kind: simpler to configure, but revocation would affect every user.
- Relying on the inference server flag alone: vLLM documents that `--api-key` protects only `/v1`,
  so the gateway enforces the key on every route as well.

## Consequences

- A `workload_credentials` table tracks which Secret belongs to which resource and when it was shown; rotation is a delete-and-recreate.
- The Hugging Face and NGC tokens stay platform-level secrets used only by controllers; they are never handed to users.
- External secret stores (Vault, external-secrets) remain out of scope; Kubernetes Secrets in the release namespace are the store.

## Implementation notes

Each instance's credential is written to two Secrets, not one:
`<kind>-<id8>-credentials` for the workload chart (Qdrant's `apiKey`, Milvus's root password)
and `<kind>-<id8>-apikey-auth` for the gateway's `apiKeyAuth` `SecurityPolicy` on the `-api`/`inf-` route.
That second policy is created with `sanitize: false`, a detail not called out in the design:
`sanitize: true` (the default) strips the API-key header before forwarding,
which would leave the workload with no key of its own to check requests against,
so the same key has to reach both the gateway's check and the workload's.
